# 8. Crosscutting Concepts

This chapter answers which rules hold across the building blocks. Each concept
states its rule, why it holds, the decisions that set it, and the page that
explains it in full.

## 8.1 Data identity and formats {#data}

| Concept | Rule | Why | Decisions | Details |
| --- | --- | --- | --- | --- |
| Identity and paths | A resource is `<dataset>/<resource path>`; a family member is `family/member`. In a cache it lies at `<root>/<entry>/<resource path>`, where the entry is `<dataset>`, or `<dataset>@<r>` for revision r > 1; on the store, at `<publication URL>/<remote prefix>[@<r>]/<resource path>`. A revision keeps the keys and changes only where the bytes are. A name keeps its meaning forever, and a purged name is never reused. | Every package computes the same place for the same file, so packages share files without coordinating, and nothing needs a lock. | [0004](decisions/0004-cache-paths-from-resource-identity.md), [0019](decisions/0019-revisions-and-successors.md) | [Why one catalogue](../deduplication.md) |
| Formats specified once | Every standardised file has one specification, a model in `ethos_data.formats`. Validation, the JSON Schemas, the templates, the strip list, the leak check, the index row and the reference tables derive from it. Keys, file names and format ids are spelled once. | Reader and writer agree, published index rows equal source rows, drafts are checked as the build checks them, and the reference cannot drift from the code. | [0006](decisions/0006-every-file-format-specified-once.md) | [File formats](../../reference/schemas.md) |
| One inventory reader | One reader reads every generated catalogue (a checkout, a published URL, a tree rendered in memory) through the metadata-source port: the index first, a descriptor on first need, each shard at most once. Data users and maintainer commands see the same resources, sidecars and missing-part error, and the build writes with the reader's shard rules. | Separate readers drift in digests, sidecars, names, errors and laziness, and maintainers must see what readers see. | [0007](decisions/0007-one-inventory-reader.md), [0005](decisions/0005-lazy-index-descriptors-and-shards.md) | [The inventory reader](building-blocks.md#inventory-reader) |

## 8.2 Settings, lookup and caches {#lookup}

| Concept | Rule | Why | Decisions | Details |
| --- | --- | --- | --- | --- |
| Settings snapshot | Every setting except the restricted caches is the first of an explicit argument, an environment variable, the account's one settings file (or the file `ETHOS_DATA_CONFIG` names instead) and the default. The restricted caches are an ordered list with no explicit argument and no default; `ETHOS_RESTRICTED_DIRS` replaces the file's list. A handle or command reads the settings once into a snapshot that names each value's source, and every later read uses it. `config show` and `print(handle.settings)` print it; `config show` numbers the restricted caches and says when the account lists none. | Settings resolve the same way however a script starts or ETHOS.Data is installed, a CI job can use a file of its own, and a results file records every input with its source. | [0010](decisions/0010-one-settings-file-per-account.md) | [Configuration](../../reference/configuration.md) |
| One lookup chain | Every file goes through five locators in order: (1) staging, (2) bundles, (3) the restricted caches, (4) the public cache, (5) a download into it. Each finds the file, passes or refuses; a refusal ends the call before any transfer. Restricted data is looked up only in the restricted caches. `plan` and `verify` run the chain in describe mode, where a refusal reads "not available here"; `fetch=False` downloads nothing and contacts no store. | `plan`, `paths`, `fetch` and `verify` agree on where a file is read, and a refusal never falls through to a download. Staging comes first, because it is one person's explicit statement; bundles before the caches, because a package's bundle is authoritative for that package; restricted data is found or refused before the public cache and the download are consulted; the public cache before the download, so a file that is there, or linked there, is never downloaded again. | [0012](decisions/0012-one-lookup-chain.md), [0011](decisions/0011-access-class-picks-the-root.md), [0013](decisions/0013-every-input-is-required.md), [0020](decisions/0020-repository-bundles.md) | [The lookup chain](runtime.md#the-lookup-chain) |
| Public and restricted caches | Each account has one public cache, for public data only: links read in place, copies it owns, downloads and the metadata cache. On the cluster every user sets it to one shared directory, the cluster's public cache: maintainers link and copy data into it, and any user's fetch downloads a missing file into it, once for everyone. Restricted data is read only from restricted caches: any number per account, read in order, each a directory whose file permissions admit one access combination; an account of public data only lists none. The public cache, the staging root and each restricted cache are separate directories with one layout. Nothing locks them: a download is hash-checked before it appears, nothing writes through a link, and a real directory is never replaced by a link. A broken link refuses the read and `verify` reports it; on the cluster a maintainer repairs it. | Cluster users read data already on shared storage in place, and each missing public file is downloaded once for everyone. Where restricted data is read follows from file permissions, not from a table someone keeps. Hash-checked downloads and links that no write goes through make sharing safe without a lock. | [0028](decisions/0028-one-public-cache-on-the-cluster.md), [0011](decisions/0011-access-class-picks-the-root.md), [0004](decisions/0004-cache-paths-from-resource-identity.md) | [The cluster computer](deployment.md#cluster); [Caches, classes and roots](../caches-and-access.md) |

## 8.3 Access, integrity and reproducibility {#access}

| Concept | Rule | Why | Decisions | Details |
| --- | --- | --- | --- | --- |
| Access, visibility and licensing | Visibility (`public`, or `hidden` with an `ethos:embargo`) decides whether a dataset's metadata is published; access (`public`, or `restricted` for licensed data and data the institute holds without publishing it) decides how its bytes may be obtained. A public dataset cannot be hidden. Unsettled licensing blocks distribution (upload; link or materialize into a cache; a bundle), not development. Keys marked unpublished are stripped from the public catalogue, and the leak check refuses a public tree that names a withheld dataset or holds such a key. | Redistribution terms vary per dataset, and silence about a licence must not read as permission. A catalogue entry grants no licence or permission. | [0011](decisions/0011-access-class-picks-the-root.md), [0024](decisions/0024-licensing-gates-distribution.md), [0027](decisions/0027-public-catalogue-releases-on-github.md) | [Licensing and immutability](../licensing.md) |
| Published objects never change | A published object never changes: uploads are immutable, and the store port never overwrites. Changed bytes become a revision (the same keys, a store folder `@<r>`) or a successor (another name). Removal goes metadata first and bytes last: withdraw, release, and purge only after a major release recorded after the removal. All data that a release of the current major describes is retained: the uploads on dCache and the copies the caches own; linked data and restricted installations change with their source. A purged dataset leaves a tombstone. | Caches and bundles verify files against the recorded checksums. If published bytes changed, copies would silently diverge or working jobs would start failing, and a release would change its meaning after the fact. Retention lets a rerun bounded to any release of the current major read the same objects. | [0019](decisions/0019-revisions-and-successors.md), [0018](decisions/0018-numbered-catalogue-releases.md), [0022](decisions/0022-dataset-status-files.md), [0023](decisions/0023-maintenance-pipelines.md) | [Paths are immutable](../licensing.md#paths-are-immutable) |
| Integrity | Downloaded and bundled files are hash-checked (SHA-256), and files read in place are checked for presence; `verify --deep` hashes on request. `verify --repair` downloads a damaged copy again into the public cache, never removes or replaces a link, and never touches restricted or staged data. It reports a broken link instead; on the cluster the report goes to the maintainers, through the internal tracker. A remote check by HEAD covers reachability and size only. | Copies are checked where they are made, and reading large data in place stays cheap. A repair only restores the recorded bytes, so it is safe in a cache other users read, and it never undoes a link a maintainer made. | [0012](decisions/0012-one-lookup-chain.md), [0020](decisions/0020-repository-bundles.md), [0028](decisions/0028-one-public-cache-on-the-cluster.md) | [Check and repair the cache](../../how-to/data-users/verify-and-repair.md) |
| Release bounds and reproducibility | A collections file names the catalogue releases it accepts: `min_version` with an optional `max_version`, or `exact_version`. Releases are named `vMAJOR.MINOR.PATCH`, and a bound may be a prefix: `exact_version: v1.3` admits every `v1.3.x`, the same bytes with the newest metadata. The settings choose the catalogue, and one outside the bounds is refused with `CatalogVersionError`. With nothing configured, the newest public release within the bounds is read from its tag. The served checkout on the cluster holds the latest release only, so packages that run there bound with `min_version` only. Development overrides are declared: staging warns once per dataset per call, a bundle ahead of the catalogue warns once per bundle, and a changed bundled file is refused or read with a warning. | A package states which releases it has been tested with, while the user chooses the catalogue. A released package resolves the same metadata later, and local experiments stay distinguishable from published data. | [0018](decisions/0018-numbered-catalogue-releases.md), [0010](decisions/0010-one-settings-file-per-account.md), [0020](decisions/0020-repository-bundles.md), [0021](decisions/0021-bundles-ahead-of-the-catalogue.md), [0026](decisions/0026-internal-catalogue-on-the-cluster.md) | [Declare the catalogue versions](../../how-to/package-maintainers/write-a-collections-file.md#catalog-version) |
| Local test divergence | A changed file in a bundle is refused until `bundle update` records it; once recorded, the change makes the bundle ahead of the catalogue. `load_bundle(DIR).fetch(…, allow_modified=True)` lets one test read the changed bytes; it keeps the recorded hashes and warns with the changed keys. Nothing repairs, republishes or updates dCache. | A developer reproduces a bug against edited test data without the edit passing as published data, and dCache keeps every published version unchanged. | [0020](decisions/0020-repository-bundles.md), [0021](decisions/0021-bundles-ahead-of-the-catalogue.md) | [Keep data in the repository](../../how-to/package-maintainers/keep-data-in-the-repository.md#update-data) |
| Bundles ahead of the catalogue | A package's bundle is authoritative for that package: the package reads what its bundle holds, even where the bundle is ahead of the catalogue (it holds recorded changes, or a dataset the catalogue does not describe). Being ahead never fails a read: every process that reads a dataset of an ahead bundle warns once per bundle, offline included, naming the datasets and both ways to realign: `propose`, or `bundle update --from-catalog`. Where the index is read anyway, a bundle behind the catalogue warns the same way. A bundle holds only data whose access and visibility are public and whose licensing is settled, and its own bytes never enter a cache. | Development never waits for the catalogue, and the warning keeps the difference visible in the package's required tests until the bundle is realigned. Every cache keeps the catalogue's bytes, so a key in a cache always means the same bytes. | [0020](decisions/0020-repository-bundles.md), [0021](decisions/0021-bundles-ahead-of-the-catalogue.md), [0004](decisions/0004-cache-paths-from-resource-identity.md) | [Keep data in the repository](../../how-to/package-maintainers/keep-data-in-the-repository.md#sync) |

## 8.4 Code structure {#code}

| Concept | Rule | Why | Decisions | Details |
| --- | --- | --- | --- | --- |
| Layers | From the bottom: model, adapters, services, presentation, with the shared modules `errors` and `report`. A module imports only from its own layer and those below, and within the services, catalogue maintenance may use data access, never the reverse. `tests/test_layers.py` checks every import, lazy ones included, with one listed exception (`Collections.main()` imports the command line); another test keeps `print` in `cli.py`, `report.py` and `formats/__main__.py`. | The reader does not depend on the writer's internals, and a violation fails a test that names the module and the import. | [0008](decisions/0008-four-layers.md) | [Components by layer](building-blocks.md#layers) |
| Typed errors and one reporter | Library code raises the typed errors of `ethos_data.errors`, each carrying its exit status: 2 for a request that cannot be served (`EthosDataError`), 1 for a refused maintenance input (its subclass `MaintenanceError`). Progress and warnings go through one reporter, which issues Python warnings outside a command. Services return results; only the command line prints (`error: …`, `warning: …`) and chooses the exit status. | Library code serves scripts, tests and the command line alike, so it neither prints nor exits, and `except EthosDataError` catches every refusal. | [0008](decisions/0008-four-layers.md) | [Exit status](../../reference/cli/ethos-data.md#exit-status) |
| Ports with fakes | The store, downloads, metadata sources and git are reached only through ports. Real adapters and fakes ship in the package; services default to the real adapters, and tests pass fakes. Adapters read no settings and raise typed errors. No test uses the network, rclone, `oidc-token` or the developer's settings. | Pipelines and the lookup chain are tested without the network or credentials, an external system can be exchanged, and downstream packages can use the fakes. | [0009](decisions/0009-ports-and-fakes-for-external-systems.md) | [Ports and adapters](building-blocks.md#ports-and-adapters) |

## 8.5 Catalogue maintenance and handoffs {#maintenance}

| Concept | Rule | Why | Decisions | Details |
| --- | --- | --- | --- | --- |
| Plan before acting | Every catalogue workflow that writes is a pipeline: every stage plans, reading but never writing, before any acts, and `--dry-run` is the plan. A refusal comes before the first write, and every action with an external effect carries a check of its result. A stage plans nothing for work already done, so a rerun does only what is left. A batch is not a transaction: completed transfers stay. | Accepting, releasing and removing a dataset take several steps whose order must not depend on memory: bytes are deleted only after a major release recorded after their removal, and a release waits for verified uploads. | [0023](decisions/0023-maintenance-pipelines.md) | [Runtime View](runtime.md) |
| Dataset state | Each dataset's `status.yaml` records its state, build input, copies, authority and an append-only history. Every command checks its step against the lifecycle while planning and records it after acting. Nobody edits the file by hand, and it is never published; maintainers commit it in their own clone and merge it by merge request. | Progress is recorded with evidence, every step is checked, a hand-written claim of an upload is impossible, and a rerun resumes from the record. | [0022](decisions/0022-dataset-status-files.md), [0026](decisions/0026-internal-catalogue-on-the-cluster.md) | [The dataset lifecycle](runtime.md#dataset-lifecycle) |
| Handoffs | The command that knows the facts drafts each handoff from a template: a proposal, a problem report, an answer, a release or removal notice, the public tracker's issue templates. Reports are scrubbed of tokens, credentials, the home directory and the account name. People post the drafts, on JuGit for restricted data and from cluster installations, on GitHub otherwise; ETHOS.Data writes nothing to a tracker. | A handoff carries the facts the tools know, forms and commands ask for the same things, and no report leaks a token or a personal path. | [0025](decisions/0025-handoff-templates.md) | [How the roles work together](../../how-to/index.md#roles-together) |
